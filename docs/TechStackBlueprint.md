# Restaurant OS — Technology Stack Blueprint

**Document ID:** ROS-STACK-001
**Status:** Adopted (03 Sep 2026) — resolves ADR-001, ADR-002, ADR-003, ADR-010, ADR-011; see `SolutionArchitecture.md` §2, §15
**Owners:** Technical Lead, Platform Lead
**Constraint:** React + Python, open-source or free-tier only

---

## 1. Purpose and constraints

This document proposes a complete, end-to-end developer tooling stack for building Restaurant OS with **React on the frontend and Python on the backend**, using only software that is open-source or has a free tier sufficient for the MVP and a controlled pilot.

Every recommendation is traced to a requirement in the canonical set: `ROS-PRD-001`, `ROS-ARCH-001`, `ROS-DATA-001`, `ROS-SEC-001`, `ROS-DEL-001`, `ROS-FEAT-001`.

Ground rules taken from the canonical documents:

- Architecture is a **modular monolith** (Documentation Hub ND-02); no microservice extraction for MVP.
- Committed baseline is a **12-week MVP** followed by a controlled pilot (Documentation Hub ND-01).
- **Stripe** is the reference payment provider behind an adapter boundary (Documentation Hub ND-03).
- Correctness beats feature breadth: no lost orders, no duplicate charges, no cross-tenant leakage (`ROS-PRD-001` section 1).

### 1.1 Decisions this blueprint resolves

ADR-001 (backend language/framework) was already resolved as FastAPI + Python 3.12 in `ROS-ARCH-001` §2 before this blueprint was written — the reasons: one language across API, async workers and the Device Agent; OpenAPI generated natively; async I/O suited to payment, SMS and real-time fan-out; trade-off accepted: no JVM throughput headroom, mitigated by the extraction points in `ROS-ARCH-001` §14.

This blueprint additionally resolves three more of the ADRs `ROS-ARCH-001` §15 lists as required: **ADR-002** (real-time transport — Server-Sent Events, §10), **ADR-003** (event/outbox strategy — PostgreSQL outbox + Dramatiq/RabbitMQ, §9) and **ADR-011** (async job queue — Dramatiq, RabbitMQ-backed, §9), superseding an earlier draft of `ROS-ARCH-001` §2 that assumed Celery and WebSocket/Ably. `ROS-ARCH-001` §2 and §15 and the `ROS-DEL-001` §21 ownership table have been updated in the same change so the canonical set stays consistent (Documentation Hub section 4).

## 3. Monorepo and workspace

Three React apps must share one design system, one generated API client and one set of event types — that is the case for a monorepo. Python does not sit naturally inside Nx, so keep it a peer: one git repository, a JS tool-root and a Python tool-root. Trunk-based development with a protected `main` and short-lived branches is already mandated (`ROS-DEL-001` section 13); `nx affected` keeps CI proportional to the diff.

| Concern | Recommended | Why | Cost | Alternatives |
|---|---|---|---|---|
| Monorepo tool | Nx (package-based) | Task graph, local computation cache, generators for the three apps and shared libs; run `nx affected` in CI. Package-based mode keeps setup light. | Free | Turborepo; bare pnpm workspaces |
| JS package manager | pnpm | Strict, content-addressed, fast; best workspace protocol for `libs` to `apps` linking. | Free | npm workspaces; Yarn 4 |
| Python workspace | uv | One lockfile across `backend`, `workers`, `device-agent`; far faster installs than pip in CI images. | Free | Poetry; PDM; Hatch |
| Repository shape | Single polyglot repo | Small team, 12-week MVP; atomic cross-cutting changes in one PR. Split later only with an ADR. | Free | Two repos with a published client package |
| Task hooks | pre-commit | One config runs Ruff, Biome, Gitleaks locally before CI; satisfies the formatting and lint PR check. | Free | Husky + lint-staged (JS only) |

## 5. Frontend apps and framework

There are three distinct surfaces with different constraints:

- **`customer-web`** — guest-first, opened from a QR scan, must render in under 2 seconds on representative 3G (`ROS-PRD-001` NFR-003).
- **`admin-web`** — dense forms and tables behind authentication (F6, F11).
- **`kds-pwa`** — installable, real-time, tolerant of Wi-Fi loss (F4).

None require server-side rendering: there is no login-wall SEO, and the public menu is already a CDN-cacheable JSON endpoint (`GET /public/menu/{branchId}`, `ROS-ARCH-001` section 11). So React SPA + Vite for all three keeps one build system for a small team.

| Concern | Recommended | Why | Cost | Alternatives |
|---|---|---|---|---|
| Framework | React 19 (SPA) | Largest hiring pool; every needed library targets it first. Server Components add nothing here without a Node server beside the Python API. | Free | Preact for `customer-web` |
| Build tool | Vite + `@vitejs/plugin-react-swc` | Instant dev server, Rollup production build, per-route code-splitting for the 3G budget. | Free | Rspack |
| `customer-web` rendering | SPA shell + edge-cached menu fetch | Static shell on the CDN; menu JSON cached at the edge with `stale-while-revalidate`. Hits NFR-003 without an SSR runtime. | Free | Next.js static export only if per-branch link previews or marketing SEO become a requirement; Nx runs it alongside the Vite apps |
| `kds-pwa` | Vite + `vite-plugin-pwa` | Workbox service worker: precache shell, runtime-cache the queue endpoint, keep last-known queue in IndexedDB for the reconnect path (F4). | Free | Hand-rolled service worker |
| Node runtime | Node 20 LTS, pinned | README already pins Node 20; pin per-repo so CI and laptops match. Node 23+ breaks the current Docusaurus build. | Free | Node 22 LTS |

**Rule of thumb:** reach for Next.js only when a page must be HTML-complete before JS runs, for a crawler or a link unfurl. For an authenticated console, a kitchen display and a post-scan ordering flow, that moment never arrives — and an SSR tier means a second language runtime to deploy, monitor and secure.

The through-line is **server state is not client state**. TanStack Query owns everything from the API, with retry and backoff mirroring the resilience patterns in `ROS-SEC-001` section 14; Zustand owns only the local bits — cart contents, the reconnecting banner, offline mode.

| Concern | Recommended | Why | Cost | Alternatives |

| API client | Orval (from OpenAPI) | Generates typed TanStack Query hooks from the FastAPI schema; regenerated in CI so a breaking API change breaks the frontend build (contract-test gate, `ROS-DEL-001` section 13). | Free | `openapi-typescript` + `openapi-fetch` |
| Dates and money | date-fns + Intl + dinero.js | Branch-timezone business rules (`ROS-DATA-001` section 5.6); integer minor units only, never float (`ROS-DATA-001` section 5.7). | Free | Day.js; Temporal polyfill |

## 8. Backend framework and data

FastAPI earns the pick on four specifics from the spec:

1. Native **OpenAPI 3.1** feeds both the typed frontend client and the `docs/contracts/openapi/` artifact (Documentation Hub section 6).
2. **Pydantic v2** with `extra="forbid"` is the "no mass-assignment, strict schema, allow-list enum" control (`ROS-SEC-001` section 9).
3. Its dependency-injection system is the clean place to resolve **tenant context, role check and the RLS session variable** per request (`ROS-ARCH-001` section 12, ADR-006).
4. Async I/O suits the Stripe, SMS, database and SSE-fan-out workload.

| Concern | Recommended | Why | Cost | Alternatives |
|---|---|---|---|---|
| Web framework | FastAPI | OpenAPI-native, Pydantic validation, DI for tenancy and auth, first-class SSE and WebSocket. | Free | Django + DRF (free admin jump-starts the Platform console; sync-first); Litestar |
| ASGI server | Uvicorn workers under Gunicorn | Proven process management, graceful reload, health probes (Sprint 0 exit criteria). | Free | Granian; Uvicorn `--workers` directly |
| ORM | SQLAlchemy 2.0 async + asyncpg | Handles the reporting projections and the many invariants; explicit enough for RLS policy work. | Free | SQLModel; Piccolo |
| Migrations | Alembic | Autogenerate plus hand-review; CI runs `upgrade head` on an ephemeral Postgres and checks reversibility (`ROS-DEL-001` section 17). | Free | Atlas |
| Database | PostgreSQL 16 | Transactional source of truth (`ROS-DATA-001` section 1); RLS for tenant isolation (`ROS-SEC-001` section 3); `FOR UPDATE SKIP LOCKED` for the outbox and queue. | Free | PostgreSQL 15 or 17 |
| Tenant isolation | RLS + request-scoped setting | `SET LOCAL app.current_tenant` in a FastAPI dependency at transaction start; policies compare the row's `tenant_id` to it. Defense in depth behind explicit authorization (`ROS-SEC-001` section 3). | Free | — |
| Money type | Decimal or integer minor units + py-moneyed | `ROS-DATA-001` section 5.7 forbids binary float for authoritative money. | Free | — |
| Internal ops screens | SQLAdmin mounted on FastAPI | Fast path for the Platform Admin console and Audit Log viewer (F6 gap analysis) without hand-building CRUD. | Free | Piccolo Admin; a dedicated `admin-web` route |

## 9. Idempotency, outbox and queue

This is the part the product cannot be wrong about: "a confirmed order must not be lost, a retry must not create a duplicate charge or duplicate kitchen order" (`ROS-PRD-001` section 1). The pattern the architecture already asks for is a **transactional outbox** (`ROS-ARCH-001` section 13) — the event row is written in the same database transaction as the order, so an event can never exist without its durable state, and vice versa. A worker drains the outbox and publishes.

| Concern | Recommended | Why | Cost | Alternatives |
|---|---|---|---|---|
| Event durability | Outbox table in Postgres | Same-transaction insert means events follow durable state (`ROS-ARCH-001` section 13); drained via `SKIP LOCKED`. No extra infrastructure for the guarantee. | Free | Debezium CDC |
| Worker and queue | Dramatiq + RabbitMQ | Dead-letter exchange, per-message ack, retry-with-backoff middleware map directly to `ROS-SEC-001` section 14 (DLQ, at-least-once, poison messages). | Free | procrastinate (Postgres only, no broker); arq or SAQ (Redis); Celery |
| Scheduled reconcilers | APScheduler in a worker | Payment-intent sweep, stuck device command, stale KDS connection, webhook-failure retry (`ROS-SEC-001` section 14). | Free | periodiq; Kubernetes CronJob; systemd timers |
| Idempotency store | Postgres `idempotency_keys` + short Redis lock | Durable record per `ROS-DATA-001` section 3.6; a Redis `SET NX PX` lock stops two concurrent requests both executing (`ROS-DATA-001` section 9). | Free | Postgres advisory locks only |
| Webhook dedupe | `webhook_events` unique on (provider, event_id) | `ROS-DATA-001` section 3.6 and INV-003; insert-or-conflict before processing, replay tooling respects it (`ROS-SEC-001` section 8). | Free | — |
| Resilience helpers | tenacity + pybreaker | Bounded exponential backoff with jitter (`ROS-SEC-001` section 14); circuit-break unstable integrations. | Free | stamina |

**Minimal-infrastructure variant:** if running RabbitMQ is unwelcome for the pilot, `procrastinate` keeps jobs, retries, periodic tasks and a dead-letter equivalent in Postgres. You lose native topic routing and mature dead-letter ergonomics; you gain one less service to operate. Record the choice in ADR-003.

## 10. Real-time and KDS transport

The spec is explicit that real-time transport is an **optimization, not the system of record** (`ROS-ARCH-001` section 9): the KDS keeps a local snapshot, resyncs via REST after a drop, and polls while the socket is down. Server-to-client push is all that is needed — status changes go back over `PATCH /order-items/{orderItemId}/status` — so SSE is the simpler correct choice over WebSocket.

| Concern | Recommended | Why | Cost | Alternatives |
|---|---|---|---|---|
| Push transport | Server-Sent Events | Auto-reconnect built in, works over plain HTTP/2, trivial to scale; enough for branch-scoped order and item events. | Free | WebSocket via a `partysocket` reconnect wrapper; `python-socketio` if you want rooms and acks |
| Browser client | `@microsoft/fetch-event-source` | Native `EventSource` cannot send an `Authorization` header; this can, plus visibility-aware retry. | Free | Native `EventSource` (avoid putting the token in the URL — `ROS-SEC-001` privacy) |
| Multi-instance fan-out | Valkey Pub/Sub via `broadcaster` | An event produced on instance A must reach an SSE client held on instance B behind the load balancer (`ROS-ARCH-001` section 14). | Free | Redis Streams; NATS |
| Resync and fallback | TanStack Query on `GET /kds/queue` + `refetchInterval` | On reconnect, refetch the authoritative queue; while SSE is down beyond a threshold, poll. Duplicate event application is harmless by design (F4). | Free | — |
| PWA offline shell | `vite-plugin-pwa` (Workbox) | Precache shell, cache last queue in IndexedDB, drive a reconnecting banner from a Zustand flag; scales to the F19 full-outage mode later. | Free | Hand-rolled service worker |

## 11. Cache and CDN

`ROS-ARCH-001` section 11 defines a layered cache for the public menu and an explicit **do-not-cache** list: settlement state, checkout validation, authorization decisions, refund balance, security context. Use **Valkey** rather than Redis proper — the open-source fork keeps you clear of the Redis source-available license, which matters under a strict "free of cost" reading.

| Concern | Recommended | Why | Cost | Alternatives |
|---|---|---|---|---|
| In-memory store | Valkey 8 | Effective-branch-menu cache, OTP attempt and cooldown counters, idempotency lock, rate-limit buckets, SSE fan-out bus. | Free | Redis OSS 7.2; KeyDB; Dragonfly |
| Client | redis-py (async) | Absorbed `aioredis`; one library for cache and pub/sub. | Free | — |
| CDN and edge | Cloudflare free plan | Unmetered bandwidth, cache rules with `stale-while-revalidate`, tag or URL purge on `menu.changed`, basic WAF and rate limiting (`ROS-SEC-001` section 9). | Free | Fastly free dev tier; bunny.net (cheap, not free) |
| Object storage | Cloudflare R2 | Menu images, QR-sticker PDFs, report exports, archived webhook payloads; no egress fees, S3 API. | Free tier, then usage | Backblaze B2; MinIO for local dev |
| S3 client | aioboto3 | Works unchanged against R2, B2 or MinIO — swap by endpoint. | Free | — |

## 12. Payments and SMS

Stripe is the canonical reference provider (Documentation Hub ND-03) and the design keeps **raw card numbers out of the backend entirely** via the provider-hosted Payment Element (`ROS-SEC-001` section 7). Both payments and SMS sit behind an **adapter boundary** so a second provider can be added without touching domain code. The SDKs are free; per-transaction and per-SMS fees are the unavoidable running cost (see section 19).

| Concern | Recommended | Why | Cost | Alternatives |
|---|---|---|---|---|
| Payment provider | Stripe (`stripe` Python SDK) | PaymentIntents plus idempotency keys (FR-007); signed webhook via `construct_event`; test mode and Stripe CLI replay. | Per transaction fee | Adyen, Checkout.com behind the same `PaymentProvider` protocol |
| Card capture (frontend) | `@stripe/react-stripe-js` + Payment Element | Tokenized, provider-hosted fields — reduces PCI scope (`ROS-SEC-001` section 7); MIT. | Free | — |
| Payment contract tests | `stripe-mock` | Official mock server; runs in CI for the `ROS-DEL-001` section 14 contract-test tier. | Free | Recorded fixtures via vcrpy |
| SMS and OTP delivery | Twilio (`twilio` Python SDK) behind an `SmsProvider` port | De-facto standard, trial credit; the adapter lets a cheaper regional carrier drop in for a single-country pilot. | Per SMS fee | AWS SNS; Vonage; Plivo; MessageBird |
| SMS in dev and CI | Console and fake provider | Logs the code locally, never in production (`ROS-SEC-001` section 6, "no OTP in logs"); contract test hits a mock. | Free | — |
| Local webhook tunnel | Stripe CLI `listen --forward-to` | Replays real events at localhost; no paid tunnel service. | Free | — |

## 13. Auth and identity

MVP auth is **OTP-only, no passwords**: guest-first short-lived customer sessions, staff access and refresh tokens with the refresh token **stored as a hash** (`ROS-DATA-001` section 3.2, `ROS-SEC-001` section 4). Do not stand up Keycloak or Ory for this — a small dependency set covers it; those belong to the F12 enterprise-SSO path.

| Concern | Recommended | Why | Cost | Alternatives |
|---|---|---|---|---|
| Access tokens | JWT via joserfc (or PyJWT) | Short-lived, role and branch-scope claims derived server-side (FR-012). joserfc replaces the unmaintained python-jose. | Free | Opaque tokens + Redis session lookup |
| Refresh and OTP hashing | argon2-cffi | Refresh tokens and OTP codes hashed at rest (`ROS-SEC-001` sections 4 and 6); rotation and revocation on `staff_refresh_tokens`. | Free | bcrypt |
| OTP generation | Python `secrets` | Cryptographically secure codes (`ROS-SEC-001` section 6); expiry, attempt cap, resend cooldown enforced with Redis counters. | Free | — |
| Rate limiting | slowapi (Redis backend) | Per-mobile and per-IP throttle on OTP request and verify (`ROS-SEC-001` sections 6 and 9) that the CDN cannot express. | Free | Cloudflare rate-limit rules (coarser) |
| Future SSO | Authlib | OAuth and OIDC when F12 lands; not wired for MVP. | Free | Keycloak; Ory Hydra |

## 14. Device Agent

A separate deliverable: a long-running process on the restaurant LAN that talks to ESC/POS printers, **persists pending commands locally**, deduplicates by `command_token`, sends heartbeats, and keeps working through transient cloud loss (`ROS-ARCH-001` section 10). Same language as the backend so the team maintains one codebase style.

| Concern | Recommended | Why | Cost | Alternatives |
|---|---|---|---|---|
| Runtime | Python 3.12 standalone app | Shared models and validation with the backend; small footprint. | Free | Go, if printer libraries suffice |
| Local durable queue | SQLite (WAL mode) | "Persist pending commands locally" and "bounded processed-token history" (`ROS-ARCH-001` section 10) with no server to run on-site. | Free | LMDB; a file-backed queue |
| Printer I/O | `python-escpos` | USB, network and serial ESC/POS; the standard MIT library. | Free | Vendor SDKs per device |
| Cloud link | httpx long-poll or SSE pull + tenacity | Agent pulls commands, posts acks and heartbeat; bounded backoff on outage (`ROS-ARCH-001` section 10). | Free | MQTT (Mosquitto) if many devices per branch |
| Packaging | PyInstaller (plus Inno Setup on Windows) | One binary for back-office PCs; restaurants rarely run Docker. | Free | Docker image where the site allows it; briefcase |
| Pairing wizard | Local FastAPI page on 127.0.0.1 | Printer discovery and credential entry (F5 gap analysis, "pairing and setup wizard"). | Free | A small bundled React page |

## 16. Security and supply chain

`ROS-SEC-001` section 19 blocks production on: an unresolved critical or high finding, tenant-isolation test failure, an authorization regression on a P1 path, a webhook signature or dedupe test failure, an **active secret detected**, or a dependency-policy violation without an approved exception. The tools below cover SAST, dependency scanning, secrets, IaC and container scanning — all free.

| Concern | Recommended | Why | Cost | Alternatives |
|---|---|---|---|---|
| Secret scanning | Gitleaks | Pre-commit and CI; enforces the `ROS-SEC-001` section 19 "secrets scan detects active secret" gate and section 10. | Free | TruffleHog; GitHub secret scanning (public repos) |
| SAST | Semgrep (open-source) | Good FastAPI and React rulesets; write custom rules — "no client tenant header", "no f-string SQL", "no float money". | Free | CodeQL (free only for public repos); Bandit (Python only) |
| Dependency scanning | osv-scanner + Dependabot | Covers both `uv.lock` and `pnpm-lock.yaml`; Dependabot opens the update PRs. | Free | pip-audit; pnpm audit; Renovate |
| Container and IaC | Trivy | One tool: image CVEs, filesystem, and OpenTofu misconfiguration scanning. | Free | Grype + Checkov |

## 17. Infrastructure and deploy

`ROS-ARCH-001` section 14 wants "one deployable API application, one or more worker processes, a shared database, horizontal scaling behind a load balancer" — and explicitly warns against premature operational complexity. That is a **Kamal-on-VPS** shape, not Kubernetes. Four environments are required: local, CI-ephemeral, staging, production (`ROS-DEL-001` section 16).

| Concern | Recommended | Why | Cost | Alternatives |
|---|---|---|---|---|
| Local environment | Docker Compose | One `compose.yaml`: Postgres, Valkey, RabbitMQ, MinIO, Mailpit, API, worker, three web apps — the Sprint 0 local-dev deliverable. | Free | Tilt; devcontainers |
| Deploy tool | Kamal 2 | Zero-downtime Docker deploys to plain hosts, rolling restarts, health checks, secret injection — no control plane to run. | Free | Docker Swarm; k3s + Helm (only if the team knows Kubernetes); Coolify |
| Compute | VPS — Hetzner, or Oracle Cloud always-free | The Oracle free tier (4 ARM cores, 24 GB) can host the whole pilot at zero cost; Hetzner is the cheapest paid step-up. | Free tier | Fly.io, Render, Railway free tiers — fine for staging, risky for production |
| Edge and TLS | Traefik | Dynamic config from Docker labels, automatic Let's Encrypt; pairs with Kamal and Compose. | Free | Caddy; nginx + certbot |
| Infrastructure as code | OpenTofu | Terraform's open-source fork — license-safe. Manage Cloudflare, DNS, VPS, R2, managed Postgres. Keep it a skeleton for MVP (Sprint 0). | Free | Terraform (BSL license); Pulumi free tier |
| Managed Postgres (non-production) | Neon free tier | Database branching gives a fresh isolated database per PR — the CI-ephemeral environment for near-zero effort. | Free tier | Supabase free tier; self-host Postgres in CI via Testcontainers |
| Production Postgres and backup | Self-hosted Postgres + pgBackRest | Point-in-time backups plus a scheduled restore-verification job (`ROS-DEL-001` go/no-go "backup and restore verified"). | Free | Neon or Aiven paid tier |
| Feature flags | Unleash self-hosted + OpenFeature SDK | `ROS-DEL-001` section 18 wants flags for "risky or incomplete optional behavior"; Unleash is the standard open-source choice. | Free | A `feature_flags` table + Redis cache; Flagsmith OSS |

## 18. Observability

`ROS-PRD-001` NFR-007 mandates a request or correlation ID on every request, with tenant and branch on logs and traces; `ROS-SEC-001` section 15 lists the exact metrics (checkout success, webhook dedupe, order-to-KDS latency, DLQ depth, cache hit ratio, database pool) and section 16 the alerts. Emit **OpenTelemetry** from the app and pick one backend — SigNoz is the shortest path to all three signals in one deploy.

| Concern | Recommended | Why | Cost | Alternatives |
|---|---|---|---|---|
| Instrumentation | OpenTelemetry SDK + auto-instrumentation | FastAPI, SQLAlchemy, redis, httpx spans; API to database to external to async publish and consume (`ROS-SEC-001` section 15). | Free | — |
| Backend (APM) | SigNoz self-hosted | Traces, metrics and logs in one OpenTelemetry-native app; build the `ROS-DEL-001` section 19 dashboards there. | Free | Grafana LGTM (Loki, Grafana, Tempo, Mimir); Uptrace; HyperDX |
| Structured logs | structlog | JSON with the `ROS-SEC-001` section 15 field list; processors scrub secrets, OTPs, card numbers and tokens before emit. | Free | loguru + python-json-logger |

| Error tracking | GlitchTip self-hosted | Sentry-compatible SDK, far lighter to run; release and regression tracking. | Free | Self-hosted Sentry |
| Uptime and status | Uptime Kuma | External synthetic checks for the `ROS-SEC-001` section 16 alerts, plus a public status page for the pilot. | Free | Gatus |
| Alert delivery | Grafana or SigNoz alerting to ntfy | Self-hostable push to phones; no paging-SaaS bill for a pilot. | Free | Alertmanager to email or Slack; PagerDuty free tier |

## 20. API and event contracts

Documentation Hub section 6 names two artifacts to maintain: an **OpenAPI** spec under `docs/contracts/openapi/` and an **AsyncAPI** event catalogue under `docs/contracts/events/`. ## 22. What actually costs money

Every framework, library and tool above is open-source or has a free tier that covers an MVP and a controlled pilot. The running costs are external services and hosting — and even those have a genuine zero-cost path for a single pilot restaurant.

| Item | Why it costs | MVP-pilot path | Rough order |
|---|---|---|---|
| Stripe | Per-transaction processing fee; no monthly fee | Unavoidable for card payments; pass-through or absorb | About 2.9% + 30 cents per transaction |
| SMS (OTP) | Carrier fee per message | Start on trial credit; AWS SNS is cheapest; rate-limit and send OTP only where policy requires (FR-004) | About 0.6 to 5 cents per SMS |
| Compute | VPS CPU, memory, bandwidth | Oracle Cloud always-free (4 ARM cores, 24 GB) hosts the full pilot; Hetzner about 5 to 15 euro per month to scale out | Zero, then about 20 USD per month |
| Managed Postgres | Only if not self-hosting production | Neon free tier for CI, preview and staging; self-host production Postgres + pgBackRest | Zero, then about 25 USD per month |
| Object storage and CDN | Storage plus, usually, egress | Cloudflare free plan + R2 (no egress fee); free tiers cover pilot volume | About zero to 5 USD per month |
| Domain | Registrar fee | One domain; TLS is free (Let's Encrypt) | About 10 to 15 USD per year |
| CI minutes | Only if over the GitHub free allowance | `nx affected` keeps most PRs cheap; self-host a runner if it bites | Zero, then usage |

## 23. ADR crosswalk

This blueprint originally resolved four of the open ADRs listed in `ROS-ARCH-001` section 15 outright (ADR-001, ADR-002, ADR-003, ADR-011) and proposed a concrete direction for the remainder. ADR-004, ADR-005 and ADR-006 have since been ratified from those proposals — see `ROS-ARCH-001` §15 for the current status of all eleven. Only ADR-007 and ADR-008 remain genuinely open: both are business/governance calls (billing currency; AI vendor, data and cost policy) that no amount of stack tooling resolves.

| ADR | Subject | Resolution | Status |
|---|---|---|---|
| ADR-001 | Backend language and framework | FastAPI + Python 3.12; Uvicorn under Gunicorn | Resolved |
| ADR-002 | Real-time transport strategy | Server-Sent Events + REST resync + polling fallback; Valkey Pub/Sub for multi-instance fan-out | Resolved |
| ADR-003 | Event publication and outbox strategy | Transactional outbox in Postgres; Dramatiq + RabbitMQ workers (or procrastinate for a broker-free pilot) | Resolved |
| ADR-004 | Device Agent transport and protocol | HTTP long-poll from cloud; local SQLite (WAL) durable queue; ack and heartbeat over HTTPS | Resolved |
| ADR-005 | Payment provider abstraction | `PaymentProvider` protocol; Stripe as the first implementation | Resolved |
| ADR-006 | Tenant context and PostgreSQL RLS | Request-scoped `app.current_tenant` setting applied in a FastAPI dependency; RLS policies on all tenant-scoped tables | Resolved |
| ADR-007 | Platform billing currency | Business decision — unchanged by tooling | Open |
| ADR-008 | AI vendor, data and cost policy | Business and governance decision — unchanged by tooling | Open |
| ADR-010 | ORM/query layer | SQLAlchemy 2.0 async + asyncpg | Resolved |
| ADR-011 | Async job queue | Dramatiq, RabbitMQ-backed | Resolved |
